# quiz：设计决策小测

目的：确认用户理解这个项目的设计选择和取舍，防止 agent 做了决定而用户不知道。

本 skill 只出题、判分、讲解。不修改代码，不顺手做其他任务。

## 1. 收集素材

按顺序读，读到够出题为止：

1. `agent/desc-*.md`（需求与设计决策文档，按编号从新到旧：`desc-1` 需求规格，`desc-2` 设计决策，`desc-3` 工具链）
2. `README.md`、`taskmgr/README.md`、`docs/*.md`（英文版；`*.zh-CN.md` 是同内容的中文版）
3. `git log --oneline -30` 和最近几次提交的 diff（看实际落地了什么）
4. 主要源码的入口、数据结构、调度/状态流转逻辑
5. 当前对话里 agent 刚做过的决定（如果用户在本次会话中调用）

用户带了参数（如 `/quiz 调度`、`/quiz 最近一次改动`）时，只围绕该范围出题。

如果项目还没有足够的设计内容（需求文档为空、没有代码），直接告诉用户"目前没有可考的设计决策"，并说明缺什么，然后结束。不要编造设计来出题。

## 2. 挑选考点

列出素材里的设计决策，每条记下：决策内容、备选方案、选它的理由、出处（`file:line` 或 commit）。

优先考这些：
- 架构划分：组件边界、谁负责什么、进程/机器之间怎么通信
- 数据与状态：任务状态机、状态存在哪、持久化方式
- 调度策略：GPU 分配、排队、优先级、抢占
- 失败处理：任务失败、机器被抢占/宕机后的恢复、重试与幂等
- 用户明确提过要求、而 agent 做了取舍的地方
- 和直觉相反、或者容易误解的选择

不考：函数名、参数默认值、文件路径这类查一下就知道的细节；纯风格问题。

选 3–5 题。用户没指定范围时，优先覆盖最近改动和影响面最大的决策。

## 3. 出题

用 AskUserQuestion，每次 1 题，等用户答完再出下一题（下一题可以根据上一题的表现调整难度）。

题型：
- **选择题**（默认）：4 个选项，干扰项必须是真实可行、在别的系统里会被采用的方案，不放明显错误的凑数项。正确答案位置随机，不加 "(Recommended)"。
- **为什么题**："X 选了方案 A 而不是 B，主要原因是？" 考理由，而不是考记忆。
- **场景题**："如果 worker 在任务跑到一半时被 preempt，会发生什么？" 考用户能否推出系统行为。

题干里不泄露答案，不写出处。用户可以选 "Other" 用自己的话答，按意思判分。

## 4. 判分与讲解

每题答完后立即反馈：
- 对 / 部分对 / 错
- 正确答案 + 一两句理由
- 出处：`file:line` 或 commit hash，方便用户去看
- 答错时，说明用户选的那个方案在本项目里会出什么问题

如果用户的答案指出了设计本身的问题（比如他的方案其实更合理），如实承认，记为"待讨论的设计问题"，不要硬判错。

## 5. 总结

全部答完后输出：

```
得分：x / n
清楚的部分：...
不清楚的部分：...（每条附出处）
待讨论的设计问题：...（如有）
```

然后把本次结果追加到 `agent/quiz-log.md`（只追加，不覆写），格式：

```
## YYYY-MM-DD（先用 date 命令确认日期）
- 范围：...
- 得分：x / n
- 不清楚的点：...
- 待讨论的设计问题：...
```

下次出题前先读 `agent/quiz-log.md`，上次没答对的点可以换个问法再考一次。
